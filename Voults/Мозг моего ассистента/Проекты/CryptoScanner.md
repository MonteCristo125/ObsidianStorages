# CryptoScanner

Go-сервис реального времени для мониторинга микроструктуры рынка на крипто-биржах. Единственный пользователь и заказчик — трейдер-скальпер (владелец репозитория), торгует руками в стороннем терминале Metascalp. Авто-торговли нет — система только наблюдает и оповещает.

- **Репозиторий:** https://github.com/MonteCristo125/CryptoScanner
- **Стек:** Go 1.22+, PostgreSQL + TimescaleDB, Telegram Bot API, HTML/JS-дашборд (отдаётся самим Go-сервисом)
- **Архитектура:** Clean Architecture — `domain → application → infrastructure/presentation`, зависимости строго внутрь
- **Процесс разработки:** свой pipeline `analyze → design → instrument` через MCP-тул `phase` и подчинённого агента `implement`; каждая нетривиальная задача — отдельная ветка `task/<slug>` с артефактами в `.claude/deliverables/<slug>/` (analysis/design/roadmap/impl-log)

Полная документация для агента — `CLAUDE.md` в корне репозитория (build/lint/test-команды, тюнинг порогов, конвенции коммитов).

## Задача 1: crypto-scanner (базовая система, до 2026-07-02)

### Проблема

Трейдер-скальпер конкурирует за раннее обнаружение крупного участника рынка (плотности в стакане, скрытый объём, всплески потока сделок, накопление открытого интереса). Готовые сторонние сканеры не годятся: чужие пороги, нет кросс-биржевой логики, нет контроля задержки, нет петли проверки собственных гипотез. Нужен свой инструмент.

### Выбранная архитектура — двухслойный скан

Рассматривались 4 альтернативы (от полной L2-реконструкции всего рынка до классического индикаторного скана) — выбран **двухслойный подход**:

1. **Широкий слой (WideScanner)** — дешёвые сигналы по всему рынку: агрегированная глубина top-N, лента сделок, объём, открытый интерес. Отвечает на «не знаю, где появится участник».
2. **Глубокий фокус (FocusManager)** — полный стакан и точный жизненный цикл плотности, но только для монет-кандидатов, поднятых из широкого слоя (автоматически по `PromotionPolicy` или вручную — Pin/Unpin). Отвечает на «отследи цикл достоверно».

Переход монеты из широкого слоя в фокус управляется `PromotionPolicy` — конфигурируемая политика (например, порог score за окно подтверждения).

### Типы аномалий (V1)

| Тип | Что обнаруживает |
|---|---|
| Плотности в стакане | Появление / удержание / восполнение / поглощение / спуфинг крупного уровня |
| Айсберги | Восполняемые уровни и сделки крупнее видимой ликвидности |
| Поток сделок | Всплеск объёма, перекос агрессии (buy/sell bias), серии сделок одинакового объёма (работа робота-исполнителя) |
| Открытый интерес | Всплеск OI, дивергенция OI и движения цены (фьючерсы) |

Пороги — **адаптивные по символу** (`ThresholdPolicy`, P90 от baseline монеты), не единый глобальный порог: у BTC и мало-ликвидного альта разный масштаб нормы.

### Ключевые компоненты (application-слой)

- `WideScanner` / `FocusManager` — два слоя скана
- `SignalPipeline` — дедупликация, агрегация кандидатов в один алерт, расстановка приоритета (поглощение плотности = высокий приоритет всегда)
- `AlertDispatcher` + `AlertChannel` (Telegram, Dashboard WS-push со звуком) — доставка
- `HypothesisEvaluator` — петля проверки гипотез: снимок цены через N минут после каждого алерта (5м/15м/1ч и т.д.), чтобы отделять рабочие сигналы от шумовых прямо в дашборде (вкладка «Гипотезы»)
- `FeedHealthMonitor` — наблюдаемость: видно, какие WS-потоки живы и есть ли lag, чтобы тишина в алертах читалась как «спокойно», а не «поток упал»

### Биржи

Восемь адаптеров реализуют единый интерфейс `domain.MarketDataSource` (OCP — новая биржа не требует правки ядра): **Binance, Bybit** (основные, глубокий фокус + широкий слой), плюс **OKX, Gate, KuCoin, Bitget, AsterDex, Hyperliquid** (широкий слой, staggered-старт при запуске, чтобы не будить rate-limit биржи одновременным REST-всплеском).

### Хранилище

TimescaleDB: таблица алертов + time-series снимков рыночного состояния (для петли гипотез). Migrations через `golang-migrate`.

## Задача 2: metrics (2026-07-02 — 2026-07-03) — скринер рынка

### Запрос пользователя

> «Надо переделать полностью всё, что есть по метрикам. Как работают сканеры вроде TaoScalp: список монет биржи, сортировка по метрикам (сделки, объём, OI, ΔOI, всплеск объёма, всплеск сделок) на разных таймфреймах (1с…24ч). Алерты должны быть настраиваемы — не работать по умолчанию, я сам создаю алерт. По умолчанию — страница со списком монет и настраиваемыми колонками, сортировкой.»

Это смена модели «система сама решает, о чём оповещать» (детекторы с зашитыми порогами) на «пользователь видит весь рынок и сам конструирует условия».

### Что построено

**Движок метрик** (`internal/domain/metrics` + `internal/application/metrics_engine.go`):
- `Timeframe` (11 значений: 1с, 5с, 15с, 30с, 1м, 5м, 15м, 30м, 1ч, 4ч, 24ч) и `MetricKind` (сделки, объём, OI, ΔOI, всплеск объёма, всплеск сделок)
- `SymbolSeries` — кольцевые бакеты на символ: 60 секундных + 1440 минутных + ~300 точек OI. «Всплеск» = текущее окно ÷ среднее по ≤12 предыдущим окнам того же размера
- `MetricsEngine` — карта символ→ряд на 32 шардированных мьютексах (не единый лок — расчёт на тысячи событий/с), горячий путь `ObserveEvent`, снапшот для API

**Охват рынка**: Binance + Bybit, фьючерсы + USDT-спот, **все торгуемые монеты** (не watchlist) — четыре независимых движка. Адаптеры бирж получили шардированные WS-подписки на сделки по всему рынку (`SubscribeTrades`, лимит потоков на соединение), листинг всех символов, REST-историю (`FetchKlines1m`, `FetchOIHistory`) для холодного старта.

**Backfill холодного старта** — минутные свечи (24ч) и история OI подгружаются с биржи при старте через worker-pool (≤4 запросов параллельно на биржу), чтобы длинные таймфреймы не были пустыми часами после рестарта.

**Конструктор алертов** (`AlertRule`, `RuleStore`/`FileRuleStore`, `RuleEvaluator`):
- Правило: биржа, охват (**конкретная монета** ИЛИ **весь рынок**), метрика, таймфрейм, оператор, порог, каналы доставки (Telegram/дашборд), cooldown
- Хранится в `data/alert_rules.json` (не в БД — работает без поднятого TimescaleDB), атомарная запись
- Оценщик — тик раз в секунду, cooldown per (правило × символ) против спама при истинном условии

**UI**: вкладка «Скринер» стала **первой и дефолтной** — таблица с сортировкой по клику, диалог настройки колонок (метрика × таймфрейм, добавить/убрать/порядок, сохраняется в localStorage браузера). Бывшая лента алертов переехала на вторую вкладку «Алерты», там же — список правил и форма их создания.

### Breaking change: тишина по умолчанию

Старые детекторы (плотности, айсберги, поток, OI-спайк) **больше не шлют алерты сразу после старта** — `SignalPipeline` инициализируется с активным пустым фильтром типов. Включаются вручную теми же чекбоксами UI, что и раньше. Причина: конструктор алертов скринера стал основным инструментом оповещений, старые детекторы — опциональная легаси-подсистема (код не удалён).

### SOLID-решения

- **DIP**: движок метрик работает через `MetricsSource`/`HistorySource`/`RuleStore` — HTTP-слой и оценщик правил не знают о конкретных биржах
- **Repository**: `RuleStore` — интерфейс, `FileRuleStore` — единственная реализация V1; замена на TimescaleDB не требует правки вызывающего кода
- **OCP**: новая биржа скринера = новая реализация `HistorySource` + подключение в composition root (`cmd/scanner/screener.go`), ядро не меняется

### Integration Verification — находки на живых данных

Финальная проверка (роадмап-шаг 12) оказалась продуктивнее самой имплементации — 9 багов найдено и починено прогонами против реальных Binance+Bybit:

1. Гонка OI-поллера и backfill за REST-бюджет IP → 429 у Binance — решено привязкой старта OI-поллера к сигналу завершения backfill биржи (не фиксированной задержкой)
2. Молчаливое усечение тела HTTP-ответа при превышении лимита `httpretry` (спотовый `exchangeInfo` Binance оказался >16 МБ) — теперь явная ошибка вместо обрубленного JSON; плюс `showPermissionSets=false` облегчает сам запрос
3. **Транзиентные сбои REST на старте раньше НАВСЕГДА отключали компонент** (пару биржа/рынок скринера, OI-поллер, backfill) до перезапуска процесса — заменено на ретраи каждую минуту до успеха, что было явным нарушением сквозного требования «непрерывность наблюдения» из задачи 1
4. WS-реконнект молчал в лог при недоступности эндпоинта — добавлено логирование первой и каждой десятой попытки (иначе «тишина» неотличима от «поток упал», что напрямую бьёт по `FeedHealthMonitor`)

Итоги живого прогона: все 4 источника отдают данные (530–609 монет на источник), backfill Binance — 530/530 символов без ошибок за 2.5 минуты, тестовое правило (`bybit`, весь рынок, всплеск сделок) дало 515 срабатываний за 50 секунд по 357 символам с **нулём нарушений cooldown**, правило пережило рестарт процесса, память — 230–380 МБ RSS.

### Артефакты задачи

`.claude/deliverables/metrics/` в репозитории: `01-analysis.md` (интервью и альтернативы), `02-design.md` (архитектура, SOLID, breaking changes), `roadmap.md` (12 шагов), `impl-log.md` (подробный лог реализации и верификации, включая все находки выше).

## Задача 3: rate-limiter (2026-07-04 — 2026-07-05)

### Как всё началось

Пользователь заметил: метрики скринера по `binance-futures` перестали обновляться. Расследование (без готовой гипотезы, чисто диагностика) вскрыло цепочку: одновременный холодный старт `backfill` binance-spot + binance-futures + OI-поллеры + легаси `WideScanner` восьми бирж — все одновременно бьют по REST-бюджету одного IP без какого-либо клиентского троттлинга. Прямой `curl` к живому Binance API подтвердил: SPOT REST банил IP кодом **418** («Way too much request weight used») прямо во время расследования, FUTURES REST в тот же момент отвечал 200 OK (раздельные бюджеты по хосту). `AsterDex` (Binance-совместимый API, но независимая инфраструктура) поймал такой же 418 при старте. Корень — пробел между дизайном задачи `metrics` (там прямо планировался «глобальный троттлер запросов на биржу») и реализацией (построен только `Concurrency=4`, лимит одновременных горутин, не лимит частоты запросов).

### Что построено

Превентивный (не только реактивный) весовой троттлер REST-запросов, полностью документирован в `docs/RATE_LIMITER.md` в репозитории:

- `internal/infrastructure/exchange/ratelimit` — `Limiter` (lazy-refill token bucket без фоновых горутин), `RoundTripper` (враппер `http.RoundTripper`, встраивается в `http.Client.Transport` ПЕРЕД уже существующим `httpretry`), `WeightFunc` — Strategy-паттерн, своя реализация на каждую из 8 бирж.
- **12 бюджетов**: `binance-spot`, `binance-spot-klines` (выделен отдельно от находки конкуренции backfill/легаси MetricsTracker), `binance-futures`, `binance-alpha`, `bybit`, `okx`, `bitget`, `gate`, `kucoin-spot`, `kucoin-futures`, `hyperliquid`, `asterdex` — единица бюджета «биржа×хост» (Binance/KuCoin имеют раздельные REST-хосты spot/futures — подтверждено живьём как независимые лимиты).
- `RATE_LIMIT_SCALE` (env, дефолт 1.0) — множитель всех бюджетов разом, без пересборки.
- `GET /api/rate-limits` — снапшот утилизации, по образцу уже существующего `/api/feed-health`.
- Троттлер встроен на уровне `http.Client.Transport` каждого REST-клиента биржи — автоматически защищает и скринер, и легаси `WideScanner` (они используют один и тот же адаптер), без отдельной интеграции для детекторного тракта.
- 3 биржи (Hyperliquid, AsterDex, KuCoin) до этой задачи вообще не имели retry на 429/418 — добавлено заодно (общий пакет `httpretry` расширен методом `Post`, т.к. Hyperliquid — единственный REST-эндпоинт всей биржи, POST-only).

### Integration Verification — честный итог

Главная цель (0 HTTP 418/429) **подтверждена четырежды независимо** — изначальная диагностика, живой прогон агента (~20 мин), независимая перепроверка оркестратора (~6 мин, `RATE_LIMIT_SCALE=5`), и три калибровочные итерации финального шага (~10 мин каждая). Ни разу не воспроизвелась.

Живые прогоны попутно вскрыли то, что вышло за рамки задачи и **осознанно не чинилось внутри неё** (правило проекта — не чинить архитектурные решения автономно):

1. **Отдельный, не связанный с троттлером баг**: метрики скринера `binance-futures` иногда замирают (WS не доставляет trade-события в движок метрик) даже при 0 HTTP-банов и полностью свободном REST-бюджете — подтверждено независимо оркестратором. WS-путь `SubscribeTrades` не проходит через REST-троттлер вовсе, так что причина в другом месте (скорее всего сам пайплайн `pumpTradesIntoEngine`/`handleShardedTradeMessage`, недостаточно инструментирован для точной локализации).
2. **Каскад REST-ресинка стакана легаси `WideScanner`** через тот же бюджет `binance-spot`, что и периодический легаси `MetricsTracker` — при нехватке токенов REST-снапшот стакана задерживается, это переполняет WS-буфер, что триггерит ещё один ресинк — потенциально неограниченный самоусиливающийся цикл. Три живые калибровки бюджета (5%/17%/80% пула) дали идентичную частоту отказов `MetricsTracker` — подозрение на структурную слабость простого token bucket (голодание тяжёлых запросов на фоне потока лёгких, без FIFO-очереди), а не просто на нехватку объёма токенов.

Обе находки заведены как отдельные задачи-предложения (spawn_task chips) для расследования отдельными циклами analyze→design→implement.

### Артефакты задачи

`.claude/deliverables/rate-limiter/` в репозитории: `01-analysis.md`, `02-design.md`, `roadmap.md` (11 шагов — вырос с исходных 9 по итогам двух живых находок калибровки), `impl-log.md` (подробности всех живых прогонов и калибровок). Deep-dive документация — `docs/RATE_LIMITER.md`.

## Побочный результат: фикс phase-server

Во время задачи `metrics` обнаружен и исправлен баг в MCP-инструменте `phase` (`~/.claude/mcp-servers/phase-server`): завершённая задача (`phase: done`) навсегда блокировала инициализацию новых задач, если её директория стояла первой по алфавиту в `.claude/deliverables/`. Поправлено — `done`-задачи больше не считаются «активными».
