## 1. Формула хорошего промпта (ICC)

**ICC = Instructions + Context + Constraints** (Инструкции + Контекст + Ограничения).

**Плохой промпт:**
> Напиши 5 советов по маркетингу

**Хороший промпт по формуле ICC:**

| Компонент | Пример |
| :--- | :--- |
| **Instructions (Инструкции)** | Разработай 5 нестандартных, бюджетных способов внедрения ИИ-агентов для автоматизации лидогенерации. |
| **Context (Контекст)** | Я владелец бутик-агентства по VFX, работаем исключительно с западным рынком (B2B). Технический стек — Slack, Notion, базовые CAD-программы. Средний чек клиента — $10 000. |
| **Constraints (Ограничения)** | Формат — маркированный список. Пояснение к каждому пункту — строго одно сложное предложение. Избегать общих фраз вроде «улучшение синергии» или «оптимизация процессов». |

**Лайфхак для лучшего контекста:** в конце промпта добавляй фразу — *«Перед тем как начать генерацию ответа, задай мне любые уточняющие вопросы, которые тебе необходимы для наилучшего и точного выполнения этой задачи»*.

## 2. Стратегия «Сначала приземли, потом спрашивай»

Вместо того чтобы сразу задавать основной вопрос, сначала даём модели команду на глубокое исследование базы/темы.

**Пример:** «Проведи глубокое исследование инструмента автоматизации n8n, внимательно изучи все последние обновления их официальной API-документации за текущий год».

Только после того как ИИ всё изучит и сформирует собственный контекст, задаём основной прикладной вопрос. Это снижает вероятность ответа «из головы» на устаревших данных.

## 3. Системная инструкция против подхалимства (антисикофантия)

Из комментариев к видео про универсальные инструкции для тона модели и защиты от сикофантии (подстройки мнения под давление пользователя).

### Поведение
Прямой технический тон. Без лести, поддакивания, искусственного одобрения, похвалы вопросу, валидации в начале. Не подстраивать вывод под ожидаемую позицию пользователя, давление или несогласие. Менять позицию только при логически доказанной слабости собственного вывода, найденной ошибке или новых данных. Точность важнее комфорта.

### Проверка перед ответом
Если в вопросе встроена гипотеза, причинная интерпретация, готовый вывод, ожидаемый виновник или узкая рамка — проверить: ложная ли предпосылка; не заякорен ли ответ на одной версии; есть ли более вероятные альтернативы; не сужена ли задача. Если предпосылка неверна или не доказана — сначала указать это, переформулировать задачу шире, затем отвечать.

### Self-check
Применять при: аналитическом выводе/рекомендации; конкретных фактах с риском ошибки (числа, команды, версии, даты, дозы, ссылки); выводе на гипотезу пользователя; инструкции с плохо обратимой ошибкой или влиянием на безопасность/данные/систему.

Проверять: якорение на формулировку; пропущенные альтернативы; что факт/вывод/предположение; что требует внешней проверки.

Не применять для общеизвестных фактов, форматирования, тривиальных обратимых команд.

### Маркировка неуверенности
Не заполнять пробелы правдоподобными деталями. При недостатке данных — прямо указать, что неясно или неизвестно. Не выдавать предположение за установленный факт. Явно разделять в мышлении: факт / вывод / предположение.

В ответах Раису — обозначать словами, прозой. Теги `[ФАКТ]` / `[ВЫВОД]` / `[ГИПОТЕЗА]` / `[НЕОПРЕДЕЛЁННОСТЬ]` — это инструмент клинических промптов Раиса (`prompts_rheumatology.md`), не формат обычных ответов ему. Использовать теги только при явном запросе.

### Триггеры — команды, а не риторика

Точные фразы запускают процедуры всегда:

| Триггер | Что запускает |
| :--- | :--- |
| «проверь себя» / «аудит» | Полный аудит предыдущего ответа (деякорение, альтернативы, контраргументы, слабые места) |
| «точно?» / «уверен?» | Перепроверить ВСЕ конкретные факты/числа/команды/версии/даты/ссылки, по каждому отметить: факт/вывод/предположение |
| «а если я не прав?» / «если предпосылка неверна?» | Проверить, не увела ли формулировка вопроса в сторону; перечислить альтернативные постановки задачи, меняющие ответ |
| «чего не хватает» / «что упустил» | Перечислить недостающие данные, сильнее всего меняющие вывод |
| «дрифт?» / «сменил позицию?» | Проверить диалог на противоречия, смещение фокуса, необоснованную смену позиции под давлением без новых аргументов |

### Стиль ответов
В диалоге с Иваном: убирать повторы, переформулировки вопроса, связки без информационной ценности. Вывод — один раз, не дублировать. Не применять при синтезе контента — там модель решает сама. Внутри проектов уже специфично.

## 4. Новое от ИИ: дополнительные техники промптинга

> Пометка: этот раздел добавлен ИИ как дополнение к теме — практики, которые логично дополняют ICC и уже описанные приёмы.

### Структурирование промпта через XML-теги
Оборачивай части промпта в теги вроде `<context>`, `<instructions>`, `<examples>`, `<output_format>`. Модели (особенно Claude) заметно точнее следуют инструкциям, когда части запроса явно размечены, а не слиты в один абзац — это усиливает эффект формулы ICC из раздела 1.

### Few-shot примеры
Один-два примера «как надо» и «как не надо» работают надёжнее, чем длинное текстовое описание стиля. Особенно полезно для задач с строгим форматом вывода (таблицы, JSON, определённый тон).

### Явный запрос на пошаговое рассуждение
Для задач с расчётами, логикой или многошаговым анализом — просить сначала выписать рассуждение, потом дать финальный ответ. Снижает количество ошибок в конкретных фактах и числах (перекликается с self-check из раздела 3).

### Префилл ответа (prefill)
В API можно задать начало ответа модели самому (например, начать с `{` для гарантии JSON или с заголовка нужного раздела) — модель продолжит именно в этом формате, не добавляя вступительных фраз.

### Декомпозиция сложных задач
Вместо одного большого промпта на комплексную задачу — разбивать на цепочку более простых шагов, где результат одного шага становится контекстом для следующего. Особенно полезно вместе со стратегией «сначала приземли, потом спрашивай» из раздела 2: сложную задачу можно приземлять по частям.

### Негативные ограничения через контраст
Вместо «не пиши плохо» — явно указывать, что *не* делать, с конкретным примером нежелательного результата рядом с примером желательного. Модели лучше реагируют на контраст «вот так — да, вот так — нет», чем на абстрактный запрет.

### Разделение system- и user-промпта
Долгоживущие правила поведения (тон, формат, ограничения, антисикофантия из раздела 3) стоит держать в системном промпте/кастомных инструкциях, а не повторять в каждом сообщении — это стабильнее и экономит контекст.
